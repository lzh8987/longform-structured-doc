# 大规模结构化多章节文档（AI 一次性成稿 · 三模式）

## 何时用

- **任务规模**：本 skill 专为**大规模长文档**设计，正常产出规模为**几十到上百页（约 5 万~15 万字以上）**；单文档通常 ≥ 3 万字、含 ≥ 3 章且每章多级标题；需引用真实工程/业务数据；有"不能照抄某参考模板""最后要 Word 提交"的约束。
- **全局默认强约束——以字数为重**：篇幅达标是长文档（尤其标书/送审）的**硬门槛**，**所有 Mode 默认以字数达标为前提**，不局限于某类场景。模型单轮难以稳定撑满篇幅，故本 skill 用三条工程手段保障达标：①动笔前先确认大纲（含 3~5 级目录）以锁定各章篇幅分配；②按章拆分为独立会话推进撰写，单章独占上下文、显著提升单章可写厚度；③用推荐结构骨架（非强制死格式）撑开篇幅。最低总篇幅仍按 Mode 与主导约束给出下限锚（B 类锚定参考方案页数、A 类锚定合同金额分级、C 类自行判断或主动询问），详见「共享基础设施·篇幅基线约定」。
- **典型场景**：技术方案、可行性研究、建设方案、规章制度、标书技术部分、咨询报告、申报材料、行业调研报告。
- **触发词**：「写一份XX建设方案」「按招标要求写技术标」「参照XX方案但不能抄」「调研一下XX写份报告」「生成可提交的 docx」「一次性把整本XX写出来」。

> 本 skill 由一次真实项目归纳而来，所有纪律与坑都经过实跑验证。Mode B 即该项目直接沉淀的方法；Mode A 抽象自一次"严格按评分项对齐目录"的标书撰写实践；Mode C 为该流水线的无约束泛化。

## 0. 模式路由（任务起点，必须先做这一步）

> 执行入口见 `orchestrator.md`（总编排：六个阶段 + 闸门，是照做清单）；本 SKILL.md 是方法与纪律参考。

**每次接到任务，先判断属于哪种模式，再进入对应链路。** 三种模式的本质区别只有三点：**结构从哪来、事实由谁背书、空缺怎么标**。

| 判定维度 | Mode A · 需求/规范驱动 | Mode B · 对标/改写 | Mode C · 调研/原创 |
|----------|------------------------|--------------------|--------------------|
| **典型任务** | 招标/投标/规范/合同模板驱动，目录必须逐条对应外部约束 | 已有范本/现有方案，产出"对标"的新版或兄弟工程套用 | 无参考材料、无要求约束，自行搜集材料编写 |
| **结构来源** | 外部约束文件（评审办法/规范书/格式要求）的条目清单——目录是其镜像 | 现有方案的结构骨架——继承合理框架、换成本工程血肉 | 调研材料驱动——先有材料再归纳结构，不套模板 |
| **事实来源** | 用户提供的规范/数据 + 缺项【待补充】 | 数据卡（本工程真实数据）+ 冲突项【待确认】 | 公开/文献证据卡（带出处）+ 不可证【需核实】 |
| **空缺标记** | 【待补充】（用户未给的确切信息） | 【待确认】（源矛盾/管理单位未核定） | 【需核实】（无可靠出处，待用户确认） |
| **最大风险** | 漏掉某评分项/条款，导致目录与要求不对齐 | 照抄原工程专属数据或特色句式 | 编造论断、结构空泛套话 |

**路由规则（按顺序判断，命中即用）：**

1. 用户给了**明确的外部约束文件并要求目录一一对应其条目**（招标要求、评审办法、技术规范书、合同模板、格式要求）→ **Mode A**。
2. 用户给了**现有方案/范本**，要求"对标""参照但不能抄""更新一版""套用到 XX 工程"→ **Mode B**。
3. 用户**只给主题、受众、范围**，无参考材料与要求约束，需自行搜集 → **Mode C**。
4. 边界模糊时（如既有范本又要满足招标条目），**先向用户确认主导约束是什么**，再选主模式；可组合：以 Mode A 的"条目对齐"为骨架，以 Mode B 的"数据卡/反抄袭"填充血肉。

> 路由一旦确定，后续 Phase 均按该模式的"起始动作 + 关键纪律"执行。模式间可叠加，但**主导模式决定目录结构的生成逻辑**。

## 0.5 工作流约定（解决"字数总不达标"——大纲前置 + 分章会话）

> 这两点是本 skill 反复实跑后定位出的根因对策：**模型在单轮会话里既要谋结构、又要堆细节、还要守反抄袭与字数，认知带宽被摊薄，单章必写薄**。以下两条为全局默认工作流，三模式通用，不随 Mode 改变。

### 0.5.1 动笔前先与用户确认大纲（含 3~5 级目录）
- **必须先有大纲、再动笔**。接到任务后，先产出一份**至少含 3 级（推荐 3~5 级）目录**的大纲草案，与用户确认后再进入撰写。
- 大纲草案须随附**每章篇幅分配建议**（依据「篇幅基线约定」的单章下限 + 重点加权），让用户在大纲阶段就能拍板：哪一章是重点、哪章一笔带过、总篇幅够不够。
- 用户反馈后锁定大纲（章节编号/标题/层级/各章重点等级/各章字数下限），后续撰写严守，**不擅自增删一级章节**。超纲调整须显式说明并经用户确认。
- 大纲确认节点同时锁定"最低总篇幅"（Mode B 取参考方案页数、Mode A 取金额映射、Mode C 取用户确认值），避免终稿才发现薄了再返工。

### 0.5.2 按章拆分为独立会话推进撰写
- **每章一次独立会话**：把"写某一章"作为一次会话任务派发，单章独占整段上下文，单章可写厚度从"六章分一份"变为"一章占满"，是解决字数不达标最直接的手段。
- **每章开头必须读素材库**：开启某章会话时，先读取**数据卡 / 禁抄清单 / 章节说明书（该章条目）**，确保单章撰写建立在统一事实与口径之上，避免前后矛盾。
- **不做结尾回写**：不强制每章结束时回写"本章关键事实交接记录"。各章的事实一致性靠素材库（数据卡为单一事实来源）+ 终检「数值回源核查表」兜底，而非靠章间手工交接。这样降低流程负担、保留撰写灵活性。
- **组装由独立步骤完成**：分章写完后，单独启动"组装校验"会话，拼接各章 md、做术语/编号/引用统一、括号数据清洗、附录生成、出 docx（见各模式链路末段与 `scripts/assemble_docx.py`）。

## 1. Mode A · 需求/规范驱动型（目录严格对齐约束）

### 适用场景
根据招标要求、技术评审办法、采购技术规范书、格式要求等**外部强约束**建立新文件——典型如写标书技术部分。核心硬指标：**目录层级必须一一对应约束条目，每个评分项/规范条款都能在目录与正文中找到落点，无遗漏、无冗余**。

### 链路（分阶段）
```
A0  条目抽取      → 解析约束文件，抽取权威"条目清单"（评分项/规范条款+分值权重+格式约束），作为唯一结构锚
A1  双向映射      → 建【条目—章节对照检查表】：每条→对应章节；每章→回指条目；查遗漏/冗余
A2  目录生成      → 据映射表生成目录（层级≤6，章节号对齐条目编号）
A3  分节撰写      → 逐条/逐小标题推进，缺数据【待补充】，紧扣真实业务场景；重点评分项加权深化
A4  组装校验      → 拼接、污染词清零、括号数据清洗、附录自动生成、出 docx
A5  覆盖复核      → 终检：每条约束在终稿中可定位落点；【待补充】汇总；重点章节深度核对
```

### 起始动作（A0 条目抽取）
把约束文件拆成**权威条目清单**并落盘（人工可审阅），字段：`条目编号 / 条目原文 / 分值权重 / 格式约束 / 对应章节(占位)`。这是后续一切结构的唯一来源，**任何目录章节都必须回溯到某条条目**。同时**向用户确认合同/项目估算金额**以确定页数下限（见「共享基础设施·篇幅基线约定」的 Mode A 金额—页数映射）；金额未知不得按默认薄章处理。

### 关键纪律
1. **先映射、后写作**：未生成【条目—章节对照检查表】并确认无遗漏前，不动笔写正文。
2. **目录是约束的镜像**：章节号尽量复用条目编号；条目之间有层级关系的，目录层级与之平行；严禁为了"好看"增删约束未要求的章节（超纲章节必须显式标注并说明）。目录编号不要过于规律，要根据业务重点丰富重点章节信息量。
3. **缺项即【待补充】，不虚构数据**：金额、年限、性能指标、人员数量等用户未给确切信息的，一律【待补充】，禁止填占位数字或臆造；已掌握的真实素材则应充分展开以满足篇幅（见「用户/业主方局外要求」第 2 条），不潦草注水。
4. **不出现未经核实的具体案例/客户/业绩/人名**；紧扣本工程真实业务场景，避免通用套话。
5. **正文段落化**：同一层级内用段落叙述，减少嵌套序号，以过渡句衔接逻辑；目录层级上限建议 5 级。
6. **语言风格**：使用文档类型惯用术语、主动语态、确定性表述，适当使用行业长句与并列结构，避免口语化和"首先/其次/最后"式机械连接词。
7. **重点章节加权深化**：依分值权重识别重点评分项（高权重=重点），对应章节分配更多字数（建议 1.5–2 倍）与更深技术细节、更多数据对比，避免各章平分秋色。

## 2. Mode B · 对标/改写型（基于现有方案）

### 适用场景
已有范本/现有方案，需要产出一份"对标"的新方案——可能是更新版本、兄弟工程套用、或同类工程改写。强调**不抄袭但继承合理结构，数据真实可回源**。

### 链路（七阶段，结构来源=现有方案骨架）
```
Phase 0  素材工程          → 解析源文件，建立素材库（大纲树/数据卡/禁抄清单/术语表/政策清单）
Phase 1  编写方法论文档    → 编制手册.md + 大纲要点.md（+可选统一执行方案.md）
Phase 2  撰写章节说明书    → 逐章锁定论点/素材/深度/衔接（动笔前定死，含重点等级）
Phase 3  分章撰写          → 单章流水线：写→反抄袭审计→改写→政策符合性→输出
Phase 4  组装·一致性校验   → 拼接、术语/编号/引用统一、污染词清零、括号数据清洗、附录自动生成、出 docx
Phase 5  专家/人工评审      → 多轮审阅报告，技术正确性拍板
Phase 6  去AI味·精修       → 消机器味、公文润色、括号数据清洗收尾，将终稿打磨成可提交版本
Phase 7  终稿 docx 交付     → 格式校验、可提交
        ↑_________________________↑
              反抄袭审计贯穿每个阶段
```

### 起始动作（Phase 0 素材工程）
把现有方案与真实素材拆成 AI 可直接调用的素材库并落盘：
1. **大纲树**：章节编号、标题、每节 `[要求]`（必覆盖内容要点）、字数预估。
2. **数据卡**：本工程**唯一真实数据来源**，按主题归集（位置/等级/参数/标准/历史/现状/既有系统…），每条标出处（源文件+页码/行号）。
3. **禁抄清单**：参考模板的工程专属数据、标志性句式、本地特殊表述。
4. **术语同义映射表**——但**行业通用术语保留原文，不强行改写**。
5. **政策强制项清单**：提取"应/须/必须/应当"，映射到章节。
6. **统计参考方案篇幅**：用 `docs_to_md.py` 解析参考方案，统计其 **Word 页数（或导出页数）与汉字字数**，在素材库登记「参考方案篇幅」，作为目标篇幅绝对下限（详见「共享基础设施·篇幅基线约定」Mode B）。

### 关键纪律（详见「红线与踩坑」）
- 数据卡是单一事实来源；撰写只引用数据卡，不自己编。
- 反抄袭 ≠ 降重：工程专属数据必须替换，模板特色句式必须重构，行业通用框架允许自然复用。
- 口径澄清优先于选边：不同源头数值若口径不同分别采用；源本身矛盾标【待确认】而非擅自选边。
- 诚实【待确认】重于编造。
- **重点章节加权深化**：在《章节写作说明书》标记每章"重点等级"（重点深化/中等/概述），重点章节分配 1.5–2 倍篇幅与更深技术细节，避免平分秋色（见「共享基础设施·重点章节深度强化」）。
- **数据织入正文、不括号化**：从数据卡取数直接融入自然语句，不写成"（数据）"注释；终稿做括号数据清洗（见「共享基础设施·数据融入自然语言与（数据）清洗」）。

### 单章流水线（Phase 3）
```
writer 生成初稿
  → similarity-audit 反抄袭审计
  → [有🔴高风险] rewriter 针对性改写（仅改高风险句）
  → 二次审计（循环至无🔴、🟡<5%）
  → policy-checker 政策符合性检查
  → [有❌未覆盖] chapter-writer 补写
  → 输出该章 md + 审计报告 + 政策报告
```
- 五个角色（writer / similarity-audit / rewriter / policy-checker / chapter-writer）的 prompt 模板见 `templates/` 目录，调用时注入本章说明书 + 数据卡相关条目。
- **章节串行、章内小节可并行**（术语/口径/数据需前后一致，章节间并行易冲突）。
- 不确定内容用 **【待确认：…】** 标注并简述原因，绝不臆测。

**反抄袭审计判定标准**

| 风险 | 判定 | 处理 |
|------|------|------|
| 🔴 高 | 整句/段与模板高度雷同（连续≥8字且为描述/分析内容），或工程专属表述未替换 | 重构叙事或替换工程数据 |
| 🟡 中 | 连续6-7字相同且为模板特色表达（非行业通用术语） | 判断：通用→保留；否→改写 |
| 🟢 低 | 行业通用术语/规范引用/政策套话重复 | 保留，无需处理 |

判断流程：通用表达→保留；含工程数据→替换；模板特色→重构；公文套话→保留；其余酌情。

## 3. Mode C · 调研/原创型（无约束、自行搜集）

### 适用场景
完全没有参考材料与要求约束，仅给定主题、受众、范围、深度，**需自行搜集材料完成编写**——典型如行业调研报告、技术白皮书、可行性研究（无范本）、专题综述。

### 链路（调研驱动，结构由材料归纳）
```
C0  界定目标      → 锁定主题/受众/范围/深度/交付格式；规划调研框架与检索策略；标记核心问题
C1  搜集建卡      → 自主检索（web/文献/公开数据），每条论断建证据卡（来源+日期+可信度）
C2  综合归纳      → 按材料归纳大纲（不预设结构、不套模板），形成大纲要点；核心问题对应章节标记重点
C3  分章撰写      → 每个论断回溯证据卡或显式【需核实】；杜绝无出处断言；数据织入正文
C4  组装校验      → 拼接、引用统一、括号数据清洗、附录（证据卡索引）自动生成、出 docx
C5  溯源复核      → 终检：论断可追溯、无编造、覆盖调研目标；【需核实】汇总；重点章节深度核对
```

### 起始动作（C0 界定目标）
先与用户确认（或自定并声明）四件事再动手：**受众是谁、要回答什么核心问题、深度/篇幅、交付格式**。模糊处先列假设，动笔前一次性抛出请用户确认，避免大规模返工。

### 关键纪律
1. **论断必须有出处**：每个事实/数据/观点都回溯到证据卡（来源 URL/文献/公开库 + 获取日期）；无法给出可靠出处的，显式标 **【需核实】**，不假装确定。
2. **材料驱动结构，不套模板**：大纲由调研结果归纳，而非先套一个"通用报告框架"再填肉；同类材料才可能复用通用骨架。
3. **区分事实与观点**：可证事实标出处；分析/预测明确为"基于XX的推断"，不混入确定表述。
4. **覆盖调研目标**：终检逐条核对 C0 锁定的核心问题是否都被回答，盲区显式标注而非回避。
5. **空缺标【需核实】**：与 Mode A/B 区分——此处空缺源于"无可靠出处"，不是"用户未给"。
6. **重点章节加权深化**：C0 锁定的核心问题对应章节标记"重点深化"，分配更多篇幅与细节（见「共享基础设施·重点章节深度强化」）。

## 4. 共享基础设施（三模式通用）

### 章节草稿目录约定
- 每章一个 md：`章节草稿/01_概述.md` … 文件内从本章一级标题开始。
- 标题层级：`#`→章(H1)、`##`→节(H2)、`###`→H3、`####`→H4、`#####`→H5、`######`→H6（≤6 级，组装脚本均支持）。
- 空缺标注统一占位符：**Mode A【待补充】 / Mode B【待确认】 / Mode C【需核实】**，便于终检自动抽取汇总。

### 篇幅基线约定（解决"产出过薄、章均字数严重不足"；**全局以字数为重，最低总篇幅按 Mode 与主导约束确定**）
- **核心原则（全局默认以字数为重）**：长文档（尤其标书/送审）**篇幅达标本身就是合规硬门槛**，所有 Mode 默认以字数达标为前提——只要不出现事实/口径错误、不潦草注水，基于真实业务素材充分扩写、把篇幅写满是正当且必要的。这与「用户/业主方局外要求」第 2 条（允许合理扩写）一致，且已升级为全局基调，不再仅限 Mode A。篇幅仍随内容规模浮动，但**每章设最低字数下限**，任何章节不得写成"骨架式薄章"；重点章节按内容权重显著加厚。最低总篇幅由 **Mode 与主导约束**共同决定，**动笔前须在《章节写作说明书》/条目映射/调研框架中锁定并登记**（见 0.5.1 大纲确认节点），避免反复返工。三种 Mode 的下限逻辑不同：

- **Mode B（对标改写，有参考方案）→ 以参考方案页数为绝对下限**：参考方案本身已通过评审/实践验证，其篇幅就是"合格线"，生成文档**页数/字数不得低于参考方案**，且不低于本类型基线（技术方案类 50 页）。执行：
  1. 动笔前用 `docs_to_md.py` 解析参考方案，统计其 **Word 页数（或导出页数）与汉字字数**，在素材库登记「参考方案篇幅」；
  2. 目标篇幅 = `max(参考方案篇幅, 本类型基线)`；若本工程内容更多/更复杂，取上限；
  3. 参考方案每章篇幅按比例摊到新文档各章，作为各章下限的参考锚（再叠加下方单章硬下限兜底）。

- **Mode A（招标/需求规范驱动）→ 以合同/项目估算金额为页数下限**：金额越大、技术越复杂，方案篇幅应显著加厚；**几十万的合同不能几页了事，几百万的项目须达百页级**。建议金额—页数映射（基线，具体阈值以用户确认为准，可在章节说明书中锁定）：
  | 估算金额 | 页数下限 | 字数下限 |
  |----------|----------|----------|
  | 50 万元以下 | ≥ 30 页 | ≥ 2 万 |
  | 50 万~200 万元 | ≥ 50 页 | ≥ 3 万 |
  | 200 万~500 万元 | ≥ 80 页 | ≥ 5 万 |
  | 500 万~1000 万元 | ≥ 100 页 | ≥ 7 万 |
  | 1000 万~5000 万元 | ≥ 150 页 | ≥ 10 万 |
  | 5000 万元以上 | ≥ 200 页 | ≥ 15 万 |
  - 金额未知或用户未给时，**主动询问合同/项目估算金额**后再套表定下限；不得按"默认薄章"偷懒。
  - 目录须逐条对齐外部约束条目——页数下限由金额撑起、条目密度由约束决定，二者共同决定篇幅。

- **Mode C（调研原创）→ 自行判断或主动询问**：无参考与约束，由 skill 据调研材料体量自定合理规模（**通常 40~120 页 / 4 万~12 万字**）；若用户未明确篇幅，**动笔前主动询问期望篇幅、或给出建议区间请用户确认**（呼应 C0 界定目标），避免自定规模偏离预期。

- **按文档类型给整体规模锚（仅当 Mode 未直接给出下限时作兜底参考）**：技术方案/建设方案/可研 50~100 页；标书技术部分/规章制度 30~80 页；行业调研/咨询报告/白皮书 40~120 页。
- **按章节角色给单章下限**（所有 Mode 通用，动笔前写入章节说明书/条目映射/调研框架；Mode B 还须 ≥ 参考方案对应章篇幅摊值，Mode A 还须 ≥ 金额表总页数/章数的合理摊分）：
  - 概述 / 背景类（工程概况、现状、需求分析）：**≥ 5000 字**。
  - 目标 / 任务类：**≥ 3000 字**。
  - 总体布局 / 架构类：**≥ 5000 字**。
  - **建设方案 / 核心技术类（重点深化）：≥ 15000 字，且占全文 30%~40%**；感知布点、模型/算法、四预场景、业务应用等须逐对象展开，不得浓缩为要点罗列。
  - 组织实施 / 保障措施类：**≥ 4000 字**。
  - 附录 / 附表不计入正文章节下限，但须随正文体量配套（如参数表、设备清单、进度计划表）。
- **用推荐结构骨架撑开篇幅（推荐、不强制死格式）**：为避免单章写成"要点罗列式薄章"，各章撰写时**建议**采用如下结构骨架把篇幅自然撑开；它是推荐模板而非强制格式，撰写者可据章节性质增删小节、调整顺序，不被死格式绑住发挥：
  - 重点章节（建设方案/核心技术类）建议骨架：`章概述段` → `分对象/分维度小节（每个对象独立成节，逐对象展开参数·现状·问题·对策）` → `关键技术路线/模型算法说明（含公式或流程，以自然语言叙述）` → `数据表/对比表（≥1 张）` → `与业务场景的结合论述` → `本章小结`。
  - 概述/背景类建议骨架：`区位与工程定位` → `建设历程与现状` → `存在的主要问题` → `建设的必要性与紧迫性` → `已有工作基础`。
  - 目标/任务类建议骨架：`总体目标` → `分阶段目标（近期/中期/远期，含指标）` → `先行先试/专项任务分解` → `预期成效`。
  - 布局/架构类建议骨架：`总体架构（分层/分域图示化描述）` → `数据流向与集成关系` → `数字孪生体/对象层级` → `与既有系统的边界`。
  - 实施/保障类建议骨架：`组织机构与职责` → `进度计划（含里程碑表）` → `资金/资源保障` → `标准规范` → `运行维护与安全`。
  - 骨架的作用是**保证每章有足量"可展开的子话题"**，从而自然达到字数下限；具体写法、小节命名、是否合并，由撰写会话自行判断。
- **重点章节加权**：在单章下限基础上再 ×1.5~2，并以"字数 + 数据密度 + 技术细节"三维同时加权；终检逐章核对是否达标（见「重点章节深度强化」）。

### 复用脚本
`scripts/assemble_docx.py` — 零依赖把「有序 md 章节 + 附录」打包成合规 docx：自动映射 `#`→H1 … `####`→H4（均为 Word 原生 Heading 样式，进大纲、可被「引用→目录」自动抓取）；**标题默认自动编号**：通过 Word 原生多级列表编号（numPr 引用 multilevel 列表）实现，编号由 Word 按位置自动计算，移动/增删章节时编号与目录**自动跟随重排**（与人工在 Word 里"多级列表链接到标题样式"等价），非写死文字；开启时自动剥掉 md 标题自带的前导编号（如 `## 1.1 系统总体架构`→`系统总体架构`）以避免重复，正文与目录一致，无需手工补编号；**编号样式与排版样式均为「模板 + 自定义」可配**，定义集中在 `scripts/templates.json`（6 套编号模板 1~6、4 套排版模板 1~4，**均支持到 6 级标题** `#`…`######`），组装前由使用者选定（见下方"组装前必问"）；`--numbering 1|2|3|4|5|6` 选编号模板，`--typo 1|2|3|4` 选排版模板（字体/字号/行距/段距/首行缩进），二者均可用 `--custom-numbering` / `--custom-typo` 内联 JSON 一次性自定义，或写进 `manifest.json` 的 `numbering` / `typography` 字段（值为模板 id 字符串或对象）；`--no-numbering` 保留 md 原编号、不做自动编号；markdown 表格转真 Word 表格（带边框、表头灰底）；自动抽取【待补充/待确认/需核实】按三类生成「附录B 空缺事项汇总」；可选 `--toc` 生成目录域——**打开即自动刷新**（settings.xml 写 `updateFields=true` 并将域标 `dirty`，Word/WPS 打开即重算目录与真实页码，免去手动"更新域"），并预填由 markdown 算出的编号目录作缓存兜底（编号格式跟随所选模板，不刷新的查看器也能看到完整目录，不会裸奔出占位符）；`--page-numbers` 生成页脚页码（域，随刷新更新）；`--max-toc-level N`（1~6，默认 6）调目录捕获层级；内嵌 A4 页边距。支持命令行参数或 `manifest.json`（title/subtitle/author/chapters/refs/source_docs/toc/page_numbers/no_numbering/max_toc_level/numbering/typography）。运行：

```bash
python scripts/assemble_docx.py \
  --title "文档标题" --subtitle "副标题" --author "编制组" \
  --chapters 章节草稿/01_概述.md 章节草稿/02_目标和任务.md \
  --out 终稿.docx --toc --page-numbers \
  --numbering 1 --typo 1
# 自定义编号（例：1 / 1.1 / 1.1.1 / （四））
# --custom-numbering '{"levels":[{"fmt":"decimal","text":"%1","suff":"space"},{"fmt":"decimal","text":"%1.%2","suff":"space"},{"fmt":"decimal","text":"%1.%2.%3","suff":"space"},{"fmt":"decimal","text":"（%4）","suff":"space"}]}'
# 自定义排版（例：正文宋体小四、1.5 倍行距、段后 6 磅、首行缩进 2 字）
# --custom-typo '{"body_font":"宋体","heading_font":"黑体","body_size":12,"line_spacing":1.5,"para_after":6,"first_line_indent":2}'
```

### 解析源文档：docs_to_md.py
`scripts/docs_to_md.py` — 把 PDF / DOCX / XLSX / XLS / DOC **拆成 Markdown 文本**，供素材工程（Phase 0 / A0 / C1）消费。零依赖优先：DOCX、XLSX 用标准库 zipfile + XML 直解；DOC 优先调用外部 `antiword`，不可用时退回纯 Python CFB 读取；PDF 用 `pypdf`；XLS 用 `xlrd`。缺失库时给出明确安装提示，不静默失败。支持文件或目录（递归）、`--out` 集中输出、`--combine` 合并。额外能力：DOCX 内嵌图、PDF 位图提取到输出目录 `img/` 子目录并在正文插 `![图片](img/xxx)` 占位（矢量图提取不到则静默跳过，需人工另行补充）；Word 样式缺失时按中文编号模式（第X章 / 一、/（一）/ 1.2 层级）兜底识别标题；`.doc` 实为改名 OOXML 时自动回退。运行：

```bash
python scripts/docs_to_md.py 源目录 --out 素材_md --exts pdf,docx,xlsx,xls,doc
# 或单文件
python scripts/docs_to_md.py 某文件.pdf
```

### 反抄袭原则（贯穿三模式，重点 Mode B）
- **数据必须替换**：模板中的工程专有数据（坐标/高程/流量/投资/地名/孔数）一律用本工程数据卡替换。
- **禁止照抄特色句式**：模板标志性并列/排比结构以本工程实际重新组织。
- **不得为不同而不同**：行业通用框架、政策套话允许自然复用，强行改写显怪异。
- **场景迁移优先**：把方法论迁移到本工程场景，而非字面改写。

### 数值一致性与回源核查（三模式通用）
最终做 **「数值回源核查表」**：逐条抽取初稿数值 → 定位源头（数据卡/证据卡/约束文件）→ 比对数值与口径 → 总表标注 ✅/⚠️。口径不同分别采用；源矛盾不擅自选边，标对应空缺符并请核实。

### 重点章节深度强化（解决"重点不突出、各章平分秋色"）
- **动笔前必须识别重点章节**，判定依据因模式而异：
  - Mode A：评分项**分值权重**高者=重点，目录与正文深度/字数随之加权。
  - Mode B：用户明确强调、且**决策影响大**的章节（如建设方案、核心系统、调度逻辑）=重点。
  - Mode C：C0 锁定的**核心问题**对应章节=重点。
- 在《章节写作说明书》（Mode B）/ 条目映射（Mode A）/ 调研框架（Mode C）中显式标注每章**重点等级**（重点深化 / 中等 / 概述）；**重点章节须达「篇幅基线约定」中的单章下限 ×1.5~2**，并同步加厚技术细节、数据对比与论证（以「篇幅基线约定」的绝对字数下限为硬指标，而非仅按比例分配），非重点章节不强行拉长但亦不得低于单章下限。
- **终检核对**：重点章节是否明显深于其他章节（字数、数据密度、技术细节三维度），杜绝"平分秋色"。

### 数据融入自然语言与（数据）清洗（解决"括号化、重复过多、不能直接提交"）
- **写作期纪律（根因）**：从数据卡/证据卡取数时，把数值**织入自然语句**，不用"（数据）"式括号注释充当论据。
  - 反例：「设计流量 [设计洪水流量] m³/s（设计洪水）」「流域面积 [流域面积] km²（某流域）」。
  - 正例：「工程按 [设计洪水流量] m³/s 的设计洪水标准进行闸体布置」「某流域面积 [流域面积] km²，……」。
  - 括号仅保留真正必要的说明（单位换算、引用出处、限定语），不承载核心数据。
- **终检清洗（Phase 4 组装 或 Phase 6 精修 必做）**：因章节独立撰写，同一数据常以括号形式在多处重复，终稿须做"括号数据清洗"：
  1. 用正则 `（[^）]*\d[^）]*）`（全角括号 + 含数字）全篇扫描"含数据的括号"；
  2. 能融入正文的，改写为自然语句并删括号；
  3. 重复出现的，仅在最贴切处保留一处，其余删除（消除各章独立导致的冗余）；
  4. 确属必要说明的（如单位换算、出处），保留；
  5. 处理后全篇不应再有"以括号承载核心数据"的句式——这是直接提交的硬门槛。

### 去AI味·公文润色（三模式通用，终稿前必做）
无论哪种模式，出终稿前都要做一轮"去机器味 + 公文润色"：消口语化与"首先/其次/最后"式机械连接词、统一术语与句式、消除 AI 套话与空洞排比、确保主动语态与确定性表述。Mode B 在 Phase 6 集中执行；Mode A / Mode C 在组装校验（A4 / C4）或终检阶段执行同一动作，不另设阶段。**本动作服务于「用户/业主方局外要求」第 1 条（结果性文件纯净度）**：不止消机器味，更要确保终稿不残留任何暴露 AI 生成过程或内部修订动机的元信息。

### 用户/业主方局外要求（产出纪律，超出标准文档规范的硬性要求）
> 以下条目不是通用公文规范，而是本 skill 使用方（业主方/建设单位）在长期文档协作中明确的"局外要求"，须作为产出纪律严格执行、不因任务而异；它们与三模式方法论正交，任何 Mode 都适用。
1. **结果性文件纯净度（不残留元信息）**：交付 docx 是给真实受众（上级主管部门、评审专家、建设单位）看的最终成果，**严禁出现任何暴露 AI 生成过程或内部修订动机的元信息**。典型禁止内容："(小白可看)"、"(响应 XX 修复)"、"给你看"、"以下是为你改了什么"、"本文为响应数据核查修复而生成"等面向用户的解释性旁白；不得体现"这是 AI 帮我生成的""这是为修复某问题而做"。除非用户明确要求，否则**最终产物就是最终产物**——干净、可直接交付。
2. **诚实占位、不虚构；但允许合理扩写**：凡用户未提供、源文件矛盾、或无法回源核实的数据/口径，一律对应空缺符（Mode A【待补充】/ Mode B【待确认】/ Mode C【需核实】），**严禁虚构事实、臆造数字或填占位值**。但"不虚构"不等于"禁止充实篇幅"——为满足篇幅下限与内容丰满，可基于**已掌握的真实性素材**做合理扩写：细化技术路线、分维度论述、补全论证链条、补充规范依据与背景；这是正常且必要的（长文档写作中篇幅本身就是合规要求之一）。扩写边界是**不潦草注水**：禁止空话套话堆砌、无信息量的车轱辘话、与主题无关的灌水；扩写必须以真实信息为骨架，不能无中生有。
3. **精确取源、不臆测标识符**：从数据卡/证据卡取数时，**原样引用源文件的精确字段名、路径、键名、编号**，严禁对其做大小写、格式或结构匹配的猜测；标识符不确定时回读源文件提取精确表述，而非凭印象书写。
4. **须达到可直接送审/交付状态**：成品须通过反抄袭审计（无工程专属数据残留）、政策符合性检查（"应/须/必须"条款全覆盖）、Word/WPS 格式合规（标准 OOXML 包可正常打开），并完成括号数据清洗与去 AI 味精修，方可交付。

## 5. 红线与踩坑经验（来自真实项目复盘）

1. **反抄袭 ≠ 降重**：目标是"没有照抄痕迹"，不是通过查重系统。行业通用表达/规范引用/政策套话允许重复；工程专属表述必须替换；模板特色句式必须重构。
2. **数据必须回源、单一事实来源**：所有真实数据归集进"数据卡/证据卡"，每条标出处。撰写只引用它，不自己编。
3. **口径澄清优先于选边**：不同源头数值若统计范围不同（如同一流域面积两个源头各给一值）分别如实采用；源本身矛盾（如高程基准两个年份版本并存）不擅自选边，标空缺符请核实，全文保持一致。
4. **疑似异常先回源再改**：多模型/多轮审阅提的"疑似错误"要回源核实，确有问题的才改；存在相反官方源或源本身并用的，**KEEP 并标注源冲突**，避免误删/误改。
5. **多模型并行要隔离**：若多模型并行编制同一文档，各自独立文件夹 + 独立命名前缀（如 `dsv4p_` / `hy3_`），互不引用、互不修改中间产物，最后人工对比择优。
6. **诚实标注、不虚构；允许合理扩写**：没有的数据一律对应空缺符（见「用户/业主方局外要求」第 2 条），严禁虚构事实或臆造数字；但已掌握的真实性素材应充分展开以满足篇幅与内容丰富度，只是不得潦草注水（空话堆砌、车轱辘话、无关灌水）。空缺符是能力边界声明，不是缺陷。
7. **无人值守自主推进**：开工前一次性把模糊需求/假设向用户确认清楚；执行中遇无法决断的问题先记住、留到人工时段一起处理，不臆测、不中途追问；每完成一 Phase 保存中间产物便于回溯。
8. **评审只读、修订另出**：专家/人工评审只出审阅报告，不改原文；修订另出报告，保留版本回溯。
9. **重点章节必须加权深化**：各章篇幅/深度按重点等级拉开差距，避免"平分秋色"式均匀铺陈（见共享纪律）。
10. **数据不得括号化堆砌**：取数即织入正文，终稿全篇清洗"（数据）"式冗余括号，否则无法直接提交（见共享纪律）。
11. **精确取源、不臆测标识符**：从源文件取数须原样引用精确字段名/路径/键名（见「用户/业主方局外要求」第 3 条），严禁对标识符做大小写/格式猜测；不确定时回读源文件，不凭印象书写。

## 6. 环境坑（必须知道，否则会卡很久）

- **解析源文档统一用 `scripts/docs_to_md.py`**：PDF/DOCX/XLSX/XLS/DOC 一键拆成 MD，零依赖优先（DOCX、XLSX 用 zipfile + XML 直解；DOC 优先 antiword、不可用时纯 Python CFB 回退；PDF 用 pypdf；XLS 用 xlrd）。缺失库时脚本给出明确安装提示，不静默失败。
- **中文 docx 组装用 `scripts/assemble_docx.py`**（基于 `python-docx` 生成标准 OOXML 包，确保 Word/WPS 可正常打开）：运行前确保 `python-docx` 已安装（本机 venv 已装）；`python-docx` 装不上时再退回零依赖手工 Open XML 兜底方案。
- **legacy .doc（Word97 OLE2）**：项目实测最稳是 `antiword` 外部命令；本机无 antiword 时脚本退回纯 Python CFB 解析（支持简单与多片段 piece table）。不要用 `tencent editor_sdk`（会报 -32603/1070）。
- **.xls（BIFF）**：`xlrd` 读；左右并列双表按双"序号"表头拆分。
- **中文字体（组装时）**：`styles.xml` 设 `eastAsia`（正文宋体、标题黑体），`ascii/hAnsi` 用 `Times New Roman`。
- **`assemble_docx.py` 的自动编号行为**：脚本**默认开启**标题与目录自动编号（Word 原生多级列表，移动/增删章节时编号与目录自动跟随重排）。编号"样式"由 `scripts/templates.json` 的编号模板（1~6，含 `fmt`/`text`）决定，组装前由使用者选 `--numbering 1|2|3|4|5|6`（或 `--custom-numbering` 内联、`manifest.numbering`）；**每层编号只引用自己那一级的计数**（如 L3 用 `%3`、L2 用 `%2`），切忌让中文层（chineseCounting）的 L3/L4 去引用上层 `%1/%2`，否则 Word 会把上层也按中文格式渲染成"一.二.1"式混搭——`templates.json` 现有 6 套模板已规避此坑（其中 `5`=工程项目建设标准式全中文「第X章/第X节/第X条/第X款/第X项/第X目」，`6`=党政机关公文式「一、（一）1.（1）」扩展到 6 级，深两级用圈码①与小写字母a）。开启时自动剥掉 md 标题**前导编号**（如 `## 1.1 系统总体架构`→`系统总体架构`，再由 Word 按位置重排为 `1.1`），避免"1.1 1.1"重复。若稿件标题已带编号且**希望保留原编号、不要 Word 重排**，组装时加 `--no-numbering`（标题按 md 原文原样渲染，无自动编号）。
- **`assemble_docx.py` 的排版可配**：字体（正文/标题/ascii）、各级标题字号、正文号、行距倍数、段前/段后（磅）、首行缩进（字符）均由 `templates.json` 的排版模板（1~4）决定，组装前选 `--typo 1|2|3|4`（或 `--custom-typo` 内联、`manifest.typography`）。改版式不必动脚本，只改 `templates.json` 即可。
- **子代理并行分章的 prompt 配方**：把"写某一章"派给子代理时，单章 prompt 必须自带六项，缺一项就会写薄或照抄——①任务背景与工程概况 ②素材库文件绝对路径清单（数据卡／禁抄清单／术语表／政策清单／章节说明书／源文 md）③**字数硬下限（明确写出数字）** ④禁抄词表与本工程替换值 ⑤空缺符规则与"严禁编造" ⑥输出文件绝对路径。实测按此配方派发，子代理单章普遍能写到下限的 1.5~2 倍且不触发禁抄。
- **源文档跨工程污染要反向利用**：对标改写（Mode B）时，务必**全文扫描参考文档中出现的"其它工程名"**。这既是禁抄检查（残留即污染源），也常是情报来源——实跑案例：某水库对标方案正文残留了参考模板厂商的平台名称（模板文案污染），反而成为确认目标工程现有平台名称的唯一线索，据实登记进数据卡并标【待确认】。
- **段首加粗短语（`**组织保障。**项目组…`）须转小标题，且层级必须按父标题动态算**：子代理产出里"段首加粗主题词＋句号＋正文"的写法大量出现时（实跑 209 处），用户认定它不像方案排版，要求转为小标题。转换铁律：新标题层级 = **最近一个标题的层级 + 1（上限 6）**，绝不能统一套某一级——实跑第一版统一转成 5 级，导致 `### 3.2.1` 下直接挂 5 级标题、跳过 4 级。转换后必查"层级跳跃"（逐个标题比对 `层级 - 上一标题层级 > 1`）。表题 `**表 1-1　xxx**` 必须排除（`^表\s*\d`），否则会被误转成标题。改前先备份目录（`cp -r 章节草稿 章节草稿_备份_xxx`），出错可无损回滚。
